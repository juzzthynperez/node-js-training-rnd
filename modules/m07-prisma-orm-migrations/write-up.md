## What I built

`modules/m07-prisma-orm-migrations/` in the ground repo:

- `prisma/schema.prisma` — the M06 schema translated into Prisma schema language: four models
  (`User`, `Task`, `Tag`, `TaskTag`), UUID String ids, `@map`/`@@map` keeping every table and
  column name in M06's snake_case, `@@unique([userId, title])` carrying `uq_tasks_user_title`,
  the junction as an **explicit** model with `@@id([taskId, tagId])` and per-side referential
  actions (`Cascade` on tasks, `Restrict` on tags) — verbatim from `schema.sql`. Generator is
  `prisma-client` with `output = "../src/generated/prisma"` (git-ignored) and
  `importFileExtension = "ts"` so generated imports match the project's `.ts` convention.
- Two migrations:
  - `20261021024629_m06_translation/` — generated by `migrate dev --name m06_translation`.
    Composite junction PK, all four indexes/uniques, FK actions verbatim.
  - `20261021025428_add_priority/` — scaffolded with `migrate dev --create-only`, then
    **hand-edited**: a `CASE` expression backfills each existing row's priority from its
    `due_date` (past-due → `high`, no due date → `low`, else `medium`) inside Prisma's
    RedefineTables rebuild, because SQLite cannot `ALTER` a column into `NOT NULL`.
    Applied on a populated 4-row table.
- `prisma7.config.ts` — filename confirmed by running `npx prisma@7 init` (≥7.10 naming; the
  brief's `prisma.config.ts` predates 7.10). Holds schema path, migrations path, `DATABASE_URL`,
  and the `migrations.seed` command. `.env` carries `DATABASE_URL="file:./dev.db"`.
- `src/db.ts` — the single `PrismaClient`, constructed at module load over an explicit
  `PrismaBetterSqlite3({ url })` adapter. One client per process; the adapter is the I/O layer.
- `src/services/task-service.ts` — replaces `store.ts` wholesale: `list` (status/`q` filters,
  `title|createdAt|dueDate` sorting with an `id` tiebreak, `skip`/`take` pagination returning
  `{ data, meta }`, data+count in one batch `$transaction`), `getById`, `create`, `update`,
  `remove`, plus `mapPrismaError` (P2002→`ConflictError`/409, P2025→`NotFoundError`/404,
  P2003→`BadRequestError`/400). Pins API writes to `DEFAULT_OWNER_ID`, the seed's fixed Alice UUID.
- `prisma/seed.ts` — M06 parity, deterministic: **4 users / 18 tasks / 7 tags / 30 junction rows**,
  fixed v4-shape UUIDs, explicit timestamps, priorities derived by the migration's own rule,
  self-verifying graded counts (incl. 2 untagged tasks, 1 unused tag, Dave's 0 tasks).
  Wired to `npm run db:seed` and chained into `npm run db:reset`.
- Proof scripts: `scripts/db-smoke.ts` (4 checks: dueDate round-trip, status default,
  `@updatedAt` bump, user-delete CASCADE) and `scripts/error-proofs.ts` (forces each Prisma code
  through the real client and the same `mapPrismaError` the service uses).
- `bruno/requests/v2/` — 8 new proof requests (filters, sort, pagination meta, priority/dueDate
  wire fields, seeded-title duplicate → 409, invalid query → 400 with per-field details), while
  M05's 15 requests stay byte-unmodified.
- `package.json` — `prisma`/`@prisma/client` in `^7` (CLI as devDep, client+adapter+better-sqlite3
  as runtime deps), scripts `db:generate|db:migrate|db:deploy|db:reset|db:seed|db:studio|db:smoke|prove:errors`.

## Why it's built this way (key decisions)

**Why this translation of the M06 schema into Prisma models, specifically?**

- **UUID String ids, not `INTEGER PRIMARY KEY`.** M06's rowid alias was a storage choice;
  the ids on the wire are M05's *contract* — Bruno asserts string ids, `isValidId` gates UUID
  shape, `08-get-missing-404` hardcodes one. When contract and storage disagree, the contract
  wins and the deviation gets documented (schema header, write-up). `@default(uuid())` keeps
  creation ergonomics.
- **Explicit junction, not Prisma's implicit M:N.** The M06 design needs a composite PK,
  a named `@@index([tagId])`, and *different* actions per side (task → CASCADE, tag →
  RESTRICT). Implicit M:N hands the junction to Prisma and flattens that control; the explicit
  `TaskTag` model reproduces `schema.sql` statement-for-statement, which is also what makes the
  M06 constraint proofs rerunnable against the new database.
- **`@map`/`@@map` everywhere.** Column and table names stay snake_case so `.schema` output
  remains diffable against M06's `schema.sql` — the translation is provable, not just claimed.
- **Both CHECKs dropped, loudly.** Prisma on SQLite has no CHECK; `ck_users_email` and
  `ck_tasks_status` are recorded as losses in the schema header, with the enforcement point
  named (input-side; M08's Zod takes over the status enum). A constraint you *know* you lost
  is a documented trade-off; one you forgot you lost is a defect.
- **`priority` is required with NO database default.** "Medium" for new API tasks is
  application policy, and policies live in the service layer; the column's only job is refusing
  NULLs. This is also precisely what forced the hand-edited migration (below).
- **Default-owner pin.** The API is userless (M05 contract) but `tasks.user_id` is NOT NULL.
  The service pins every write to one seeded owner whose id is a shared constant
  (`00000000-0000-4000-8000-000000000001`, imported by `seed.ts` too). Because the API's whole
  world is one owner, the DB's per-owner unique enforces exactly M05's global-409 rule —
  the three layers stay aligned: API global-409 ⊂ DB per-owner unique ⊂ globally-unique seed.

**What did you have to hand-edit in the `--create-only` migration, and why couldn't `migrate dev`
generate it for you?**

- The CLI can diff *structure*; it cannot know what *value* each existing row's new required
  column should hold. On a populated table `migrate dev` says so outright — "Added the required
  column `priority` … There are 4 rows in this table, it is not possible to execute this step" —
  and the scaffold's `INSERT INTO new_tasks … SELECT` copies every column *except* `priority`,
  so it could only fail the new NOT NULL.
- The hand-edit is exactly one thing the diff could never contain: the `CASE` expression
  (`due_date` past the authored cutoff → `high`, NULL → `low`, else `medium`), folded into
  Prisma's own RedefineTables skeleton (create new table → copy with backfill → drop → rename →
  recreate indexes). Everything else stayed byte-identical to the scaffold, so the diff between
  generated and shipped IS the teaching content.
- The cutoff is a fixed literal (`2026-10-21T00:00:00.000+00:00`, the migration's authored
  date): migrations are authored-time artifacts and the SQL must be deterministic on every
  replay. On a fresh clone the backfill runs over zero rows — the normal trainee path — and
  priorities come from the seed instead.
- Safety note carried from M06: `DROP TABLE tasks` performs an implicit `DELETE FROM` when FKs
  are enabled, which would silently CASCADE `task_tags` away. The migration sits at a point in
  history where the junction is provably empty (verified before applying, true on every fresh
  replay), and the SQL header states that assumption instead of hiding it — SQL cannot assert it.

**How did you map `P2002`/`P2025`/`P2003` onto your existing M05 error handler?**

- At the *service seam*, in one function: `mapPrismaError(err, context)` inside
  `task-service.ts`. It recognises `Prisma.PrismaClientKnownRequestError` and returns the
  matching M05 `AppError` — `ConflictError` (409, preserving M05's exact duplicate-title
  message), `NotFoundError` (404, id in the message), `BadRequestError` (400) — or returns the
  error *unchanged* when it isn't a known code, so programmer errors stay 500s and nothing
  leaks. `middleware/error-handler.ts`, `errors.ts`, and the envelope are untouched; handlers
  already `throw` AppErrors, so the rendering path is literally the M05 one.
- P2003 → **400**, not 409: a foreign-key violation means the caller referenced something that
  doesn't exist — bad reference, not state clash. (The brief allows 409-or-400.)
- P2003 is unreachable through the tasks-only API (the owner id is a pinned constant), so its
  mapping is proven at the seam by `npm run prove:errors` — forcing all three codes through the
  real client — rather than claimed. P2002 and P2025 are proven twice: at the seam *and* live
  through HTTP (Bruno `03`/`v2/07` → 409, `08`/`12` → 404).
- One deliberate fidelity catch from the pre-PR review: M05's update checked duplicate titles
  *before* existence, so `PATCH <missing-uuid> {"title": "Buy milk"}` answered **409**, while a
  naive Prisma `update` answers 404 (P2025 first). The service restored the v1 ordering with an
  explicit pre-check — behavior preservation includes error *precedence*, which no test asserted.

## How to build it (teach it to the next trainee)

**Adding a required column to a table that already has data — the reasoning, using `priority`.**

1. **Decide what kind of column it is before touching SQL.** Three cases, in order of
   preference: (a) a constant default is acceptable → SQLite's plain
   `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT <const>` is one line and safe on a populated
   table; (b) the value must be *derived from existing rows* → you need a backfill; (c) the
   column must be derived AND constrained with no default (our `priority`) → the ALTER route is
   closed, because SQLite offers no way to add a NOT NULL column without a constant default,
   and no way to alter a column's constraints at all. We chose case (c) deliberately: the
   default is policy (service layer), the column only refuses NULL.
2. **Edit the schema first.** Add the field to `schema.prisma` — the schema is the source of
   truth and the diff engine reads it. Run it against a copy of real data if you have one; the
   tool will refuse out loud on a populated table (that refusal *is* your confirmation you
   needed a hand-edit).
3. **Scaffold, don't generate-and-run:** `npx prisma@7 migrate dev --create-only --name
   add_priority`. `--create-only` writes the folder without applying anything — your edit point.
   Read the generated SQL: it is Prisma's standard RedefineTables shape (create `new_tasks`,
   copy, drop, rename, recreate indexes) minus any knowledge of your data.
4. **Check what the copy would destroy *before* you write the edit.** The drop+rename rebuild
   touches every row and every FK pointing at the table — `SELECT COUNT(*) FROM task_tags`
   (junction state), list the FKs, decide whether child rows must be preserved inside the
   migration (save/restore) or whether history guarantees they're empty (our case, stated in
   the SQL header).
5. **Hand-edit only the value source.** Keep the scaffold; add the derived column to the
   `INSERT … SELECT` as a `CASE` expression (or a two-phase `ADD COLUMN` nullable → `UPDATE`
   backfill → rebuild, if you want the phases visibly separate). Use a fixed timestamp literal
   for anything "relative to now" — the SQL must replay identically forever.
6. **Apply with `migrate dev`, then verify *data*, not just schema:** the backfilled rows
   (`SELECT title, due_date, priority FROM tasks ORDER BY priority`), the final DDL, the
   indexes, `PRAGMA foreign_key_check`. All four went into `evidence/m07/hand-edit.txt`, whose
   replay script re-runs the whole story from an empty database.
7. **Never edit a migration that has been applied** — recorded history must replay identically
   on every machine. If you got it wrong *before* applying, deleting the unapplied folder is
   legal (we did, once, in the opposite direction: see "What tripped me up"). If it's applied
   and wrong, you write a *new* migration that fixes it.
8. **Fresh-clone reality:** every trainee who runs `npm run db:reset` replays both migrations
   on empty tables — the backfill is a no-op there, and the seed supplies the values. That is
   the path the DoD grades, and it's why the seed uses the same derivation rule as the
   migration: migrated-era and seeded-era data are indistinguishable.

## Concepts worth explaining

**`migrate dev` vs `migrate deploy` (my own words).** `migrate dev` is the *authoring* tool and
it is opinionated: it diffs your schema against the migration folder, generates whatever is
missing, applies pending migrations to your local database, prompts you when it needs a name or
detects drift, refuses to scaffold changes it can't execute on real data, and — via `reset` —
will happily drop the whole database because it assumes a development machine. It changes
state, including your data. `migrate deploy` is the *auditor*: it reads the folder as recorded
history, replays anything not yet in the target's `_prisma_migrations` table, in timestamp
order, exactly as written — no diffing, no prompting, no generating, no resets, safe against a
production database. Rule of thumb: authoring on your machine → `migrate dev`; shipping the
authoring results anywhere else → `migrate deploy`. (`db push` is the third mode: it makes the
database match the schema with *no* history at all — prototyping only, because there is nothing
to replay later.)

**What the lock file and the generated client actually are.** `prisma/migrations/
migration_lock.toml` is one line — the provider (`sqlite`) — and its whole job is to stop a
teammate on Postgres from "helpfully" diffing your SQLite history into a different dialect;
history is provider-locked the moment it exists. The generated client (`src/generated/prisma/`,
12 files of plain TypeScript after `npx prisma@7 generate`) is *build output that happens to be
project code*: typed from your schema, imported by `db.ts`, never hand-edited, and git-ignored
because it's reproducible from `schema.prisma` + the pinned Prisma version — which is also why
`prisma generate` must be run explicitly after install, after every schema change, and in CI,
or the first clone dies on a missing import.

## What tripped me up

- **npm's install-script gate blocked three packages silently** — `prisma` (preinstall),
  `better-sqlite3` (its native build), `@prisma/engines` (postinstall). Install "succeeded",
  binaries missing. `npm install-scripts approve <pkg>` each, then `npm rebuild`. Worse: my
  unpinned `better-sqlite3` grabbed v13 while the adapter requires `^12.6.0` — two *native*
  copies, two bindings to build, one of them failing node-gyp. Pinning the direct dep to
  `^12.6.0` deduped to a single 12.11.1 (verified with `npm ls`).
- **Windows fnm trap, one level deeper:** `fnm exec --using=24 -- npm` fails ("program not
  found") because npm resolves as `npm.cmd`. It's `fnm exec --using=24 -- npm.cmd …` everywhere.
- **Class-name casing:** the adapter exports `PrismaBetterSqlite3` (lowercase "qlite3"), not
  `PrismaBetterSQLite3` — a `SyntaxError: does not provide an export named …` at first boot.
- **I guessed a migration folder timestamp.** `--create-only` had already written its own
  folder (`…025324_add_priority`); I wrote mine to a *guessed* `…025428_add_priority`. Two
  folders → `migrate dev` applied the naive one first → the predicted NOT NULL failure, a
  rolled-back transaction, and a poisoned history row (`finished_at NULL`). Recovery for an
  unapplied attempt: delete the bad folder, drop the local `dev.db`, replay the real sequence.
  Lesson: the tool owns folder names; never create them by hand next to its output.
- **History surgery needs the schema to travel with it.** Stashing migration 2 while
  `schema.prisma` still declared `priority` made `migrate dev` see drift and demand a *new*
  migration name — an interactive prompt, which hung the shell until timeout. Schema era and
  migration set are one unit; to replay eras, move both or neither (the final replay kept
  schema v1 until the populate ran, then restored both together).
- **Prisma 7.10.1 no longer auto-seeds on `migrate reset`.** `migrations.seed` sits correctly in
  `prisma7.config.ts` and `npx prisma@7 db seed` runs it ("Running seed command …"), but
  `migrate reset --force` finished with empty tables. Fixed by chaining:
  `"db:reset": "prisma migrate reset --force && tsx prisma/seed.ts"` — which is the DoD's
  "reset *plus* the seed script" as one command anyway.
- **Prisma's AI consent guard** on `migrate reset` (7.10.x): it refuses destructive resets from
  an agent without explicit user consent + `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` set to
  the exact consent text. Correct behavior, worth one line in the material's troubleshooting —
  humans get an ordinary prompt.
- **Client/schema drift caught by types, twice:** after adding `priority`, the old populate
  script failed typecheck with P2011 at runtime ("Null constraint violation on priority") —
  exactly the class of error the generated types exist to stop. And the pre-PR reviewer caught
  two real contract drifts no test could see (update error precedence; the `""` description
  echo — that one is irreducible: the M06 schema's `NOT NULL DEFAULT ''` cannot distinguish
  "cleared" from "never set", so it's documented, not faked).

## What I'd do differently

- **Ship the schema→migration diff as a rendered artifact, not prose.** The single most
  teachable file in this module is "generated scaffold vs hand-edited" side by side; today that
  lives in `hand-edit.txt` as a transcript. A committed `docs/hand-edit-diff.md` (or two SQL
  files kept for diffing) would make the comparison instant without replaying anything.
- **Default `pageSize` should not silently paginate a v1 client.** GET `/tasks` with no params
  now returns 20 of 18 (fine) but would return 20 of 400 — v1 returned everything. Right call
  for a paginated v2, but it's a documented behavior change the material must say out loud
  (it does, §6/§10); if I started over I'd make "no params" = "no cap, meta still present"
  and paginate only when asked.
- **`description` needs a nullable column if the wire must echo `""`.** The v1-vs-v2 difference
  above is a *schema* decision inherited from M06; `TEXT NULL` would preserve both wire
  behaviors exactly. I kept M06's DDL as the schema of record, but the trade-off deserves a
  name in the decision list, not a footnote.
- **Don't pre-check duplicates twice.** `create` relies on P2002 (one round trip, DB is the
  authority); `update` pre-checks for precedence fidelity (one extra query every PATCH). If the
  contract allowed 404-first, the pre-check disappears and both paths become identical catch
  blocks. Contract fidelity chose the cost; I'd negotiate that contract earlier next time.
- **Wire the CI story.** The arch doc's deploy sequence (`migrate deploy` + `prisma generate`
  in CI) is explained but not demonstrated — no workflow file exists in the ground repo yet.
  M07 explains it; a `deploy.md` recipe or actual workflow would prove it.
- **A module `README.md` was deferred** (the material carries setup), but M06 shipped one and
  the asymmetry between modules will confuse anyone browsing the ground repo cold.
